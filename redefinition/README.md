# Redefinition — what this repository actually is

> Read this before the root `README.md` if you are trying to understand
> what you are holding. The root README tells you how to *run* it. This
> tells you how to *think about* it.

This repository is **three distinct things** that grew in one place. They
have different maturity, different value, and different claims. Conflating
them is the single biggest way to misread this repo — in either direction
(dismissing it as an unfinished app, or inflating it into "infrastructure"
it is not yet).

| Layer | What it is | Honest status |
|---|---|---|
| **1. The football app** | Amateur-football matchmaking (Elixir/Phoenix LiveView/Postgres). | **Real.** Built, 156 tests/0 fail, runnable. Pre-launch blockers documented. |
| **2. The protocol kernel** | A deterministic, self-verifying reference for proximity-trust mesh semantics (identity, canonical encoding, signed ingest, witnessed rank, wire framing). | **Real, but bounded.** A *self-consistent reference kernel*, validated in simulation and frozen into a versioned, byte-exact contract — **not** a proven interop standard. |
| **3. The runtime / ecosystem** | A Rust node runtime, real BLE/NFC transport, a phone client, a node OS, third-party implementations. | **Aspirational.** Unbuilt. Named targets in the docs. Zero of it exists. |

## Not yet (not present facts)

Stated bluntly so the boundary cannot be misread. Football United is
**not yet**:

- a running serverless phone network;
- a Rust runtime;
- a BLE/NFC transport;
- a standards ecosystem;
- infrastructure with external adoption.

These may become future paths; today they are aspirational, not present
facts.

## Already real vs. potential vs. aspirational

Be precise about which column a claim sits in.

**Already real (you can verify it today):**

- The app runs and is tested.
- The kernel's outputs are deterministic and reproducible (Ed25519 is
  RFC 8032; fixed seeds → fixed bytes).
- The behavioral/property tests assert *relationships* (sign/verify
  round-trips, encode/decode invariants, median bounds), not copied
  snapshots. These are what make the kernel trustworthy.
- The conformance vectors are *generated by running the reference*, not
  hand-typed — and an independent code path re-derives them.
- The **methodology** — formalize behavior → freeze semantics → verify
  implementations — was actually practiced here, end to end.

**Potential (true only if invested in):**

- Verification infrastructure / compliance tooling.
- A simulation/research platform for trust & ranking dynamics.
- A systems-engineering portfolio artifact.

**Aspirational (do not market as possessed):**

- "Protocol standard," "standards authority," "interop ecosystem."
  These require the thing that **has not happened**: an independent
  implementation, by other code, that reproduces the contract.

## The legitimacy threshold

The conformance harness today compares the Elixir reference against
snapshots **generated by the same Elixir reference**. That proves
*determinism and regression-safety*. It does **not** prove the semantics
are externally reproducible. It is a self-consistent reference kernel —
not yet a proven interop standard.

The repository crosses from *self-referential* to *externally
reproducible* the first time an implementation written **without reading
the Elixir** reproduces `fu/conformance/vectors.json`.

That event — and only that event — earns the word "conformance" in its
strong sense. The rules for what counts are in
[`SECOND_IMPLEMENTATION.md`](SECOND_IMPLEMENTATION.md). They are defined
*before* any attempt, on purpose: rules written after the fact are
rationalizations of whatever shortcuts were taken.

Status: **the threshold is not crossed.** An independent Python
implementation reproduces every v6 vector — but its author had
contaminated context, so by its own statement it is a *spec-sufficiency
audit*, not a clean-room crossing. No *uncontaminated* independent
implementation exists yet. See [`CLEANROOM_READINESS.md`](CLEANROOM_READINESS.md)
and [`THIRD_IMPLEMENTATION_PLAN.md`](THIRD_IMPLEMENTATION_PLAN.md).

## The durable asset

If every other layer were deleted, the thing that survives — and the
thing most worth carrying forward — is the **methodology**, not this
codebase: write the behavior down as executable, freeze it as a
byte-exact contract, then verify implementations against it instead of
debugging emergent behavior. That pattern is reusable across domains and
is independent of whether Football United ever ships.
