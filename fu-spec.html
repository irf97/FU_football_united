Functional
Specification.

What Football United does, stated as testable requirements. This is the behavioural contract — the architecture and current state live in fu-dossier.html; this document is the spec. Each clause is numbered for traceability to tests.

1 — Scope & terms

What this covers.

FU is matchmaking for amateur/pickup football: discover or be matched to a game on a real pitch, fill exact positions, get balanced teams, play rated, settle results by peer vote, and carry an inspectable rank. "MUST" = required and test-locked; "SHOULD" = expected; "MAY" = optional/configurable.

TermMeaning
QueueA scheduled match slot at a field with a format & per-position capacity. State: open → locked → confirmed → completed/cancelled.
Soft joinMembership status:"queued", not committed ("interested").
Lock-inA commitment (locked_at set). Leaving afterwards is penalised (§5).
Main positionGK / DEF / MID / FWD — the only vocabulary the matchmaking engine uses.
Sub-positionA display variant of a main (e.g. CB, CDM, ST). Never reaches matchmaking.
Witness(Network spec) a friend who replicates and vouches for your rank.
2 — Identity & authentication

Phone OTP, abuse-resistant.

  1. MUST authenticate via phone one-time code; a player record is created on first successful verification.
  2. MUST rate-limit code requests to 5 per phone per 15 minutes; excess returns a rate-limited error.
  3. MUST cap verification attempts at 5 per active code; on the cap the code is burned and a new one is required. Consumed codes MUST NOT be replayable.
  4. MUST deliver codes through a pluggable adapter (Fu.SMS.Adapter); the default logs. A real provider MUST be configured before production.
  5. MAY expose an admin login gate; in this build it is a shared password and is explicitly not production auth.
3 — Profile & positions

Identity is display; the engine speaks the main 4.

  1. MUST let a player set: display name, an optional bold nickname shown above it, nation (from a curated list, shown with a flag), and birthdate (age is derived, never stored as a number).
  2. MUST let a player set a default sub-position per main (Defender/Midfield/Forward; GK has no variant). Each sub MUST belong to its own main; cross-main values are rejected.
  3. MUST derive nothing in matchmaking from a sub-position. Quotas, fill, balance and matching MUST only ever read GK/DEF/MID/FWD. (Test-locked invariant.)
  4. MUST display the chosen sub-position wherever a position is shown to a human (home card, profile, lobby/match/post-match rosters, browse list), falling back to the main label when unset.
  5. MUST let a player compose an avatar (legend → face/hair, kit → colours/pattern, jersey colour, number) with a live preview.
  6. MAY let a player choose a UI theme; the choice persists per device.
  7. MUST let a player declare availability windows used by auto-match.
4 — Queues & matchmaking

Two journeys: ASAP vs organized.

  1. MUST provide a Quick-match surface that actively searches and surfaces eligible immediate matches ("pops"), soonest kickoff first, each showing distance and average rating so the player can decline. Accepting a pop MUST both join and lock-in (§5).
  2. MUST provide a Browse surface listing scheduled queues with per-position fill, who is queued and what they play, region/time/format/rated filters, and lock progress.
  3. MUST assign each joiner a main position from their preferences (primary → secondary → fill-mode any open); reject when no slot fits.
  4. MUST let a friend-group queue as an atomic unit — all members placed or none.
  5. MUST rate only 8v8 and 7v7; other formats are casual. Formation quotas are doubled across both teams.
  6. MUST open a persistent per-queue chatroom once ≥ the minimum members have joined; non-members may read, members may post.
  7. MAY assume all fields are owned — there is no external booking gate on confirmation.
5 — Lock-in & bail penalties

Commitment, and the cost of breaking it.

  1. MUST treat joining as soft ("interested"). A soft member MUST be able to leave freely with no penalty.
  2. MUST let a player explicitly lock in (a commitment). Accepting a quick-match pop is equivalent to locking in.
  3. MUST confirm a queue the instant every quota slot is filled by locked members (fast path) — independent of any timer.
  4. MUST, at the lock deadline, force-lock everyone still merely queued (timer expiry = lock-in), then resolve: confirm / extend once (30 min) / cancel.
  5. MUST allow a locked player to leave ("bail"), but it MUST ban them:
    When they bailBan
    More than 24h before kickoff1 day
    Within 24h of kickoff1 week
  6. MUST stack the ban onto any existing suspension (never shorten it) and surface the ban end time to the player. The bail action MUST require explicit confirmation.
  7. MUST record a semantic event for both free leaves and penalised bails.

Rationale. Lock-in makes "match is good to go" meaningful. Bailing is allowed because real life happens, but it is costly and escalates the closer to kickoff — protecting the other 15 people who committed.

6 — Lobby & captaincy

Teams, captains, swaps.

  1. MUST auto-balance a confirmed queue into Team A / Team B; balancing MUST terminate for every format.
  2. MUST resolve captaincy by a sequenced claim window (keeper priority → top-ranked → open → random fallback) with automatic resolution by a deadline.
  3. MUST support mutual-consent position swaps within a team.
  4. MUST show live lock progress and let an un-locked member lock in, and a locked member bail (§5).
  5. SHOULD provide ephemeral team/match/group chat in the lobby.
7 — Tactics

Captain manages; the squad previews.

  1. MUST let the captain of a team set that team's formation, style, and a free-text instruction note (≤ 280 chars).
  2. MUST reject any tactics edit by a non-captain, or by a captain editing the other team ({:error,:not_captain}) — enforced in the context, test-locked.
  3. MUST show every other squad member a live, read-only preview plus a position-grouped lineup board.
  4. SHOULD default to a sensible formation/style so a preview always exists.
8 — Live match

Synced clock, captain-run.

  1. MUST provide an in-play screen with a clock synced across all participants via the match topic.
  2. MUST restrict kickoff, pause, resume and the final whistle to the captain; everyone else sees state read-only.
  3. MUST exclude paused time from elapsed played time.
  4. MUST, on the final whistle, record the score, complete the match, finalize ranks, and route to post-match — idempotently (re-submission never double-applies).
9 — Post-match & voting

Soft signals.

  1. MUST open a peer-voting window (MVP / best defender / keeper score) for 24h after match end.
  2. MUST let a player skip; two consecutive full skips trigger a one-time rank penalty (§10).
  3. MUST weight opponent-cast recognition above own-team recognition.
10 — Ranking engine

Deterministic, inspectable, append-only.

  1. MUST write one append-only rank event per participant per rated match, carrying a breakdown of every weighted component.
  2. MUST be idempotent — re-finalizing a match never moves ranks twice.
  3. MUST never mutate a past event; corrections are append-only amendments (disputes).
  4. MUST clamp rank to [30.0, 100.0]; new players start 50.0.
  5. MUST apply the weight table:

11 — Friends, groups, chat

The social graph.

  1. MUST support friend requests by phone, accept/decline, cancel, and an invite link.
  2. MUST let a player form a friend-group and queue it as a unit (§4.4); only the leader picks the queue.
  3. MUST persist queue chatroom messages so late joiners read back.
12 — Admin

Operator console.

  1. MUST gate /admin behind the admin credential.
  2. MUST list players with status (idle / in-queue / in-match), specs and avatars, and allow suspension.
13 — Non-functional

Quality attributes.

  1. MUST keep all participant screens in lock-step via PubSub; the server is authoritative (no optimistic success shown for unconfirmed actions).
  2. MUST keep the rank ledger deterministic and reproducible from events alone.
  3. MUST ship with an automated test suite; every load-bearing invariant (matchmaking-vocabulary, captain-guard, lock/penalty, OTP abuse, rank idempotence) MUST be test-locked.
  4. SHOULD use only GPU-composited motion, gate it on reduced-motion, and reserve the lime accent for moments that land.
  5. SHOULD degrade gracefully offline where the architecture allows (see §14).
14 — Network (P2P) specification

The server-less direction (research-grade).

This section specifies the target proximity-trust model. It is validated in deterministic simulation to 10k users; it is not field-implemented. It is normative for the intended design, not for the current shipped build.

  1. MUST distribute state peer-to-peer; a device persistently replicates its friend graph and transiently caches proximity peers on a TTL.
  2. MUST keep per-device storage O(network), not O(history) — updated state with a bounded recent window + checkpoint, not an unbounded log.
  3. MUST derive a player's canonical rank as the median of their witnesses' view — never the player's own copy. A lone node MUST NOT be able to forge it; only the whole witnessing group colluding can.
  4. MUST relay a held record toward the subject's witnesses (subject-directed relay) and share instantly with co-present friends; it MUST NOT blind-flood strangers' data.
  5. SHOULD use NFC as the high-trust handshake and BLE/Wi-Fi-Aware for bulk relay; steady-state exchange SHOULD fit an NFC tap.
  6. MAY promote sustained acquaintances to provisional witnesses to solve the friendless-bootstrap gap (open problem).
15 — Out of scope / open

Explicitly not specified yet.

  1. Synthesising a brand-new match from solo queuers (current quick-match selects existing eligible queues).
  2. Push/interstitial when a queue confirms while the player is on another screen.
  3. Self-sovereign keypair identity and real BLE/NFC transport (prerequisite for §14 in production).
  4. Real SMS provider and secret-stored admin credential (launch-critical, not yet built).
  5. Format downgrade (e.g. 8v8→7v7) at the lock deadline — current behaviour is confirm / extend-once / cancel.
