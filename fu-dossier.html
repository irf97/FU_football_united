Football United —
the whole picture.

A working amateur-football matchmaking app built on Phoenix/LiveView, and a peer-to-peer proximity-trust network proven in simulation to 10,000 users. This document is everything: architecture, data, lifecycle, every feature, the research, the tests, and the honest gaps.

00 — Executive summary

One sentence, then the truth.

Football United (FU) is ranked-queue matchmaking for pickup football — find a real game on a real pitch, fill exact positions, balanced teams, rated play, peer-voted results. It is deliberately ordinary so it can be the distribution channel and incubator for the real bet: a server-less, proximity-trust networking protocol where state lives on players' phones and propagates by physical co-presence.

The app is built and tested (116 green tests, all 17 audited features wired end-to-end). The network is validated in a deterministic simulation to 10k users — it works with a flat storage footprint and ~100% delivery — but it is simulation, not field-tested BLE/NFC, and one design problem (friendless bootstrap) remains open. Nothing in this document is overclaimed; gaps are stated in §14.

The app sells the experience. The network is the company. Football is how you get enough phones in the same place, often enough, for a trust network to become real.

02 — Product

Two journeys, one pitch.

QUICK MATCH · /queue

Get a game ASAP

Press QUEUE. The system pops eligible immediate matches (soonest first) showing distance + avg rating so you can decline if it's too far or too low. Accept = lock in — a commitment.

BROWSE · /browse

Get organized

Scheduled queues you join deliberately ("interested"), then Lock in when you're sure. Position-by-position fill, who's queued and what they play, lock progress.

Around the match: a per-queue chatroom (opens at ≥3), a lobby with auto-balanced teams and a sequenced captain claim, a live in-play screen with a synced clock and captain controls, post-match peer voting, and a deterministic, inspectable ranking ledger. Friends, friend-groups that queue together, an avatar identity system, and a password-gated admin console round it out.

Event-sourcing (the load-bearing decision)

Rank is an append-only RankEvent ledger — every change carries a breakdown map so "why did my rank move?" is always derivable. Corrections are amendments, never mutations (Dispute). Match completion is multi-party (captain submits, peers attest/vote). This is exactly the structure a gossip-replicated P2P system is made of — the migration path swaps transport, not the domain.

Realtime

PubSub topics per queue (queue:<id>), the lobby (lobby:<id>), the match (match:<id>), and a global queues topic. LiveViews subscribe and reload on change — every screen stays in lock-step without optimistic lies (the server round-trips and pushes truth).

06 — Match lifecycle

Queue → lock → confirm → match → rank.

Queue state is the spine: open → locked → confirmed → completed (or cancelled), with a soft-join / hard-lock overlay on memberships.

JOIN (soft, status:"queued") BROWSE: deliberate QUEUE: Accept-a-pop │ │ │ (Accept = join+lock) ▼ ▼ ▼ ┌───────────── interested ─────────────┐ LOCK IN ──────────────────┐ │ can still leave │ (locked_at set, committed)│ └───────────────────────────────────────┘ │ │ ▼ │ ┌─ every quota slot filled by LOCKED members ───┘ │ → FAST PATH: state = "confirmed" (no Resolver wait) │ T-3h lock deadline ─┤ Resolver: lock_all_queued (timer expiry = forced lock) │ → confirm | extend-once (30m) | cancel ▼ LOBBY (/lobby/:id) Balance.assign_teams → A/B · sequenced captain claim │ · mutual-consent swaps · chat · lock progress ▼ MATCH (/match/:id) synced clock · captain kickoff/pause/resume │ · captain TACTICS (squad previews) · "final whistle" ▼ Matches.submit_result/3 → complete · Ranking.finalize_match (idempotent) ▼ POST-MATCH (/postmatch/:id) peer voting (MVP/defender/keeper, 24h) ▼ RANK LEDGER append-only RankEvent + breakdown

The lock model (the seam, now closed)

  • Soft join = "interested", can leave.
  • Lock in = commitment; leave returns {:error,:locked_in}; irreversible pre-kickoff.
  • All locked → instant confirm (fast path on every lock; no Resolver tick needed).
  • Timer expiry = forced lock: the Resolver locks everyone still queued, then resolves on the locked set.
  • Quick-match Accept = lock-in (a pop is a commitment; decline if too far / rating too low).

Fields are assumed owned → no booking gate on confirmation.

08 — Identity, positions, avatars, themes, tactics

The player-facing systems.

Positions — sub as the position, main derived for the engine

You set a default sub-position per main in profile (GK has none): Defender → LB/CB/RB/LWB/RWB/SW, Midfield → CDM/CM/CAM/LM/RM, Forward → LW/RW/SS/CF/ST. On home you swap which main you'll play; the UI shows your variant (DEF pill reads "CB"). Hard invariant, test-locked: quotas/fill/balance/matching only ever see the main-4 — the sub is display-only, asserted by PositionDetailTest.

Identity

Optional bold nickname over the real name, nation (curated list + flag), birthdate → computed age. Shown on the home card, profile, and across rosters.

Avatars

Inline-SVG mini-footballers: 39 legends (skin + 7 hair styles: short/mid/buzz/bald/curly/long/mohawk), 24 kits with 5 jersey patterns (solid/stripes/sash/checker/hoops), spotlight backdrop + depth shading. Compact swatch picker with live 120px preview. No JS, identical at 28px or 120px.

Themes

Four palettes — Dark (default), Midnight, Pitch, Daylight + System — switch in Profile, persist per device. Both --fu-* tokens and daisyUI base colors switch together; lime soul preserved across all.

Tactics (captain/manager UI)

On the match page: the captain of a team edits formation (4-3-3 … 4-5-1), style (Balanced/Defensive/Possession/Counter/High-press/Direct), and a 280-char instruction note; the rest of the squad sees a live read-only preview + a positions board. Captain-guard is in the context and test-locked — a non-captain, or a captain editing the other team, gets {:error,:not_captain}.

09 — Ranking engine

Deterministic, inspectable, append-only.

Every rated match writes one RankEvent per participant whose breakdown enumerates each weighted component — the answer to "why did my rank move?" is always derivable from the ledger alone. Idempotent via a (player, queue, "match") unique index.

ComponentWeight
Outcomewin +1.5 · draw +0.3 · loss −0.8
Goal / assist+0.6 each / +0.4 each
Opponent MVP / best-defender vote+2.0 / +1.6
Own-team MVP/defender+0.6 (flat, weighted lower)
Opponent keeper score (GK only)(median − 5) × 0.3, clamp ±1.5
Skip-vote penalty−10 (2nd consecutive full skip)
No-show−15; 2nd in 60d → −15 + 14-day suspension
Decay0.3 / idle week toward 50 after 90d idle (suspended exempt)

Rank clamped to [30.0, 100.0]. Rated formats: 8v8 and 7v7. The math is property-tested (clamp idempotence/monotonicity) and the finalize pass is transactional + idempotent.

10 — The P2P thesis

Kill the server.

The app bundle and its data distribute peer-to-peer, BitTorrent-style; state lives on phones and propagates by physical proximity. BLE/Wi-Fi-Aware = cheap presence/gossip; NFC tap = the high-trust channel (key exchange, co-signing a result). Trust is a gradient: stranger → acquaintance (repeated co-presence) → friend (persistent replication).

Group-witnessed rank: your rank isn't self-asserted — it's the median of what your witnesses (friends who replicate you) hold. A lone node can't forge it; only the whole clique colluding can. Forgery cost = group size. This is the same event-sourced ledger the app already uses, with the transport swapped.

11 — The simulations

Not vibes — deterministic, to 10,000 users.

Three pure in-memory models (Fu.Mesh / .V2 / .V3), each TDD'd for its invariants (15 mesh tests), each with a seeded scale harness (bench/mesh_*_scale.exs) run at 100 / 1k / 10k over 60 rounds on a geographically-clustered swarm.

Model @10kPer-device storageWitness deliveryTypical payloadVerdict
v1 · replicate-all2.3 MB, growing— (global)219 KBScuttlebutt blow-up
v2 · friends + TTL40 KB flat5.5%p95 240 BStorage solved, delivery starved
v3 · + relay + acquaintance146 KB flat~100% (97% maj / 100% ≥2)p95 480 B (avg 6.6 KB)Holds end-to-end

What v3 added

  • Subject-directed relay — a carrier pushes your record toward your witnesses, not just holds it.
  • Instant friend-share — friends present at a match persist your fact immediately.
  • Proximity-over-time → acquaintance — repeated co-presence promotes a peer to a long-retention tier; absence (not per-tick erosion) lapses it. ~8.6 acquaintances/node, bounded.
  • Closeness filter — no blind-flooding strangers' data; relay toward witnesses or share about people you're close to. This keeps storage bounded.

Honest readings of the numbers

  • Storage is O(your network), not O(history) — flat 1k→10k while matches grew 10×. Scuttlebutt problem solved.
  • Payload p95 480 B fits an NFC tap; rare 6–37 KB relay catch-ups want BLE/Wi-Fi-Aware. The two-tier transport is now justified by data, not hand-wave.
  • Canonical rank is self-tamper-proof and group-collusion-only (property-tested).
  • Open: 7–8% friendless "orphans" have no persistent witnesses — bootstrap unsolved (likely fix: promote acquaintances to provisional witnesses; not yet validated).
  • It is a deterministic simulation. Real BLE/NFC (range, pairing UX, iOS background limits, NFC being a cm tap not a pipe) is untested.
12 — Why football markets the network

Every mesh dies for lack of co-located nodes. Football doesn't.

  • Recurring co-presence is the activity — 16+ people, same pitch, weekly. Built-in density + repeat encounters: exactly what makes v3 converge.
  • The graphs are one graph — social = football = replication topology. Teammates are your witnesses; the squad is the trust quorum.
  • The copy is true — "no servers, works with no signal on the pitch, your stats can't be faked unless your whole squad lies."
  • The viral loop is physical — to play you bring people to a place; every match seeds nodes by construction.

BitTorrent rode media; WhatsApp rode SMS; FU rides pickup sport to prove and seed a general proximity-trust protocol. (Full pitch: fu-network-pitch.html.)

14 — Honest gaps & open questions

What is NOT done. Stated plainly.

Pre-launch blockers (app):

· No real SMS adapter — Fu.SMS is a pluggable behaviour but only the log stub exists; OTP prints to server log.

· Admin password hardcoded in source (login_live.ex) — acceptable demo gate, not real auth; move to a secret store.

Network (research) open problems:

· Friendless bootstrap — 7–8% orphans have no witnesses; fix sketched (acquaintance → provisional witness) but unvalidated.

· Simulation, not field — no real BLE/NFC implementation; identity is still server-side OTP. Self-sovereign keypair migration is the real next work and is unbuilt.

· "No servers" still needs minimal bootstrap/discovery infra — edge-tolerant, not literally zero.

Product seams (deliberate, flagged)

  • Quick-match selects existing eligible queues; it does not yet synthesise a brand-new match from solo queuers.
  • No push/interstitial when a queue you're in confirms while you're elsewhere (PubSub updates only screens you're on).
  • Lobby→match needs a human click; captain drives kickoff (no auto-advance).
  • One pre-existing cosmetic compiler warning (lobby_live.ex ungrouped handle_event) — not a bug.

Roadmap (in order)

  1. Real SMS adapter + secret-store the admin gate (launch-critical).
  2. Keypair / self-sovereign identity (everything P2P depends on it).
  3. Acquaintance-as-provisional-witness → close the orphan gap; re-run harness.
  4. Quick-match synthesis (form new matches from solo queuers) + "match ready" push.
  5. Real BLE/NFC transport prototype on the existing event log.

Environment gotchas (hard-won):

· One mix process at a time — server + test share a compile lock; stop the server before mix test.

· Port 4000 zombies: kill the listener PID + stray beam before restarting, or the new server silently keeps serving old code.

· CSS edits need a manual Tailwind rebuild (_build/tailwind-windows-x64.exe) + server restart; the dev watcher is unreliable here.

· Always git-bash + source ../devenv.sh. Never WSL (different Elixir/Postgres).

· Login: any seeded number (e.g. +31610000001); OTP prints to the server log.
